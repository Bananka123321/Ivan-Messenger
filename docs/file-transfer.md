# Передача файлов

Файлы передаются по тому же TLS-соединению, что и сообщения, обычными JSON-пакетами.
Двоичные данные кодируются в base64 и идут чанками по `FILE_CHUNK_SIZE` = 256 КБ
(после кодирования ~350 КБ, меньше лимита пакета в 1 МБ). Максимальный размер файла — 100 МБ.

Все константы и построители пакетов — в `common/protocol.h`, эталонные пакеты — в `tests/contract/`.

## Загрузка на сервер

```
Клиент                                          Сервер
  | fileUploadInitRequest(dialog_id, filename,     |
  |   mime_type, kind, size_bytes, sha256) ------> | проверка полей и участия в диалоге,
  |                                                | запись в files (status = uploading)
  | <------------- fileUploadInitResponse(file_id, offset)
  |                                                |
  | fileChunk(file_id, offset, data) ------------> | offset должен совпасть с uploaded_bytes
  | <------------- fileChunkAck(offset = принято байт)
  |        ... пока offset < size_bytes ...        |
  | fileChunk(последний) ------------------------> | SHA-256 файла == заявленный?
  | <------------- fileChunkAck(completed = true)  | да: status = complete
  |                или success = false,            | нет: status = failed, файл удалён
  |                error = "Hash mismatch"         |
  |                                                |
  | sendMessage(type = Image/File/Voice, file_id) >| имя, размер и MIME берутся из БД
```

Следующий чанк клиент отправляет только после подтверждения предыдущего, поэтому
исходящая очередь сервера не переполняется и порядок чанков всегда известен.

## Обрыв связи и докачка

Сервер хранит в `files.uploaded_bytes`, сколько байт уже принято. После переподключения
клиент узнаёт это значение одним из двух способов:

- `fileUploadStatusRequest(file_id)` → `fileUploadStatusResponse(offset, status)`, если `file_id` сохранился;
- повторный `fileUploadInitRequest` с тем же файлом: сервер находит незавершённую загрузку
  этого пользователя в этом диалоге с тем же SHA-256 и размером и возвращает прежний `file_id` и `offset`.
  Так докачка работает даже после перезапуска приложения.

Если клиент прислал чанк не с тем `offset` (например, ответ на предыдущий чанк потерялся),
сервер отвечает `success = false, error = "Offset mismatch"` и в `offset` указывает, с какого места продолжать.
Повторная запись с того же места безопасна: всё, что в файле после `offset`, отбрасывается.

## Скачивание

```
  | fileDownloadRequest(file_id, offset) --------> | файл complete и пользователь — участник диалога?
  | <------------- fileDownloadResponse(offset, data, filename, mime_type, kind, size_bytes, sha256)
  |        ... offset += размер data, пока offset < size_bytes ...
```

Клиент сам запрашивает следующий чанк, поэтому докачка — это запрос с сохранённого `offset`.
Прогресс хранится в локальном SQLite-кэше (`ClientPart/App/FileCache`). После скачивания клиент
сверяет SHA-256 с полученным в ответе.

Для чужих и несуществующих файлов сервер отвечает одинаково: `File not found`, чтобы по ответу нельзя было
понять, существует ли файл с таким id.

## Хранение

| Где | Что |
|---|---|
| Таблица `files` (PostgreSQL) | владелец, диалог, исходное имя, MIME, тип, размер, SHA-256, имя на диске, прогресс, статус |
| Каталог `storage.path` из `config.json` (по умолчанию `storage/`) | сами файлы под случайными именами из 32 hex-символов |
| `file_cache.sqlite` на клиенте | скачанные файлы: путь на устройстве, прогресс, готовность |

Исходное имя файла никогда не используется как путь на диске.

Пример секции конфига сервера:

```json
"storage": { "path": "/var/lib/messenger/files" }
```

Для существующей базы таблицу нужно создать миграцией:

```bash
psql -U <user> -d <db> -h 127.0.0.1 -f ServerPart/sql/migrations/001_files.sql
```
